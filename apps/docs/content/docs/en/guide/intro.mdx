Intelligent Generative UI without a component catalog — the model builds pages on UI SDK and DESIGN.md. Open Intelligent UI lets a model answer with an interface: it writes Markdown mixed with tags, and a renderer in your product turns that stream into a surface the reader can use — with state, data through tools, motion, and decisions handed back to the model.

## Where it sits [#where-it-sits]

Two approaches are already in use: composing from a component catalog, and putting a whole page in a sandbox.

| Approach | The model writes | What you get | What it costs |
| --- | --- | --- | --- |
| Catalog composition (A2UI, OpenUI, json-render) | References to components you registered | Your design system, real behavior, safety | The interface can only be what the catalog holds |
| A page (HTML and JavaScript in a sandbox) | Anything | Any shape | No design system, no real widget behavior, isolation to manage, hard to stream |
| Open Intelligent UI | Markup that composes primitives, behaviors, drawings and your components | Any shape, in your design system, with real behavior | A language the model has to be taught, and a renderer to trust |

Behavior and look are given to the model separately:

| Foundation | What it gives the model |
| --- | --- |
| [UI SDK](https://ui-sdk.dev/docs) | The behavior of 55 components (focus, keyboard, selection, popups, accessibility) with no look of their own |
| [DESIGN.md](https://github.com/google-labs-code/design.md) | Colors, type, radius, spacing and motion tokens, with prose that says how to use them |
| Layout primitives and presets | `<card>`, `<row>`, `<grid>`, `<text>` and the rest; `<Chart>`, `<Stat>`, `<DataTable>` for content UI SDK doesn't have |
| HTML, SVG and scoped CSS | Drawing material for what no component covers: an allowlist of tags |
| A small expression language | State, derived values, lists, formatting. Interpreted, never run as JavaScript |

## What comes built in [#what-comes-built-in]

Everything below works with no configuration. Each row can be replaced or added to.

| | Built in | To change it |
| --- | --- | --- |
| Renderers | React, Vue, Svelte, Solid, Web Components | [Getting started](/guide/start) |
| Designs | Paper (the default), Noir, Heritage, Signal, each with light and dark | [Design](/guide/design): your DESIGN.md, another library's, or a theme stylesheet |
| Components | 15 layout primitives, 55 UI SDK components (367 parts), 2,410 Lucide icons, 6 preset widgets | [Your components](/guide/components): `defineComponent`, `defineWidget` |
| Charts | bar, line, area, donut, pie, spark, drawn as SVG with no dependency | [Charts](/guide/charts): ECharts, G2, Recharts or your own engine; adds scatter, radar, funnel |
| Motion | 8 entrances, stroke drawing, 3 loops, stagger, enter and exit, shared-element morph, in CSS | [Motion](/guide/motion): Motion, GSAP, the Web Animations API or your own engine; your own presets |
| Checks | A checker for a reply and the message that asks the model to fix it | [Correct output](/guide/correctness) |

## How a reply becomes an interface [#how-a-reply-becomes-an-interface]

1. You build a system prompt with `buildSystemPrompt`. It teaches the markup and describes your design, your components and your tools.
2. The model replies with markup. You pass the text so far to `<IntelligentUI>` on every chunk.
3. The renderer parses what is complete, holds back a half-written tag, and draws. State stays as the reader left it while more arrives.
4. The reader uses the interface. Controls change state, queries read your tools, handlers call them.
5. When the interface calls `send()`, you add that to the conversation and ask the model again.

## Highlights [#highlights]

Freer than a component catalog, safer than a sandboxed HTML page: one markup language, five renderers, a live prompt → stream → check → repair loop, and a safety model built for untrusted model output. Wire a host in [Getting started](/guide/start); see [Correct output](/guide/correctness) for the checker and repair path.
